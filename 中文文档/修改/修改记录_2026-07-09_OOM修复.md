## 二、排查结论

### 2.1 38 次重启原因 = 内核 OOM killer

journalctl 明确证据：

```
Jul 09 10:30:08 fastapiGmgn.service: Main process exited, code=killed, status=9/KILL
Jul 09 10:41:42 fastapiGmgn.service: Main process exited, code=killed, status=9/KILL
```

`status=9/KILL` = 内核 OOM killer 直接 SIGKILL，不是异常退出。

### 2.2 机器内存现状（修复前）

```
total 3.6G / used 2.8G / available 839M / swap 9.9G（用了 3G）
```

占用大头：
- Trae IDE node 720M
- OpenClaw gateway node 343M
- 2 个 Next.js server 300M
- fastapiGmgn 余量 ≈ 1.5G

### 2.3 fastapiGmgn OOM 的具体元凶

`trade_stream.py` / `trade_backfill.py` 的 `_extract_trade_info` 返回的 detail 都有一行：

```python
"raw_data": str(tx_data)[:20000],   # 每条 tx 留 20KB 原始 JSON
```

WebSocket 实时推送一条 BUY 就塞一条 20KB 进 Redis，backfill 一抓 100 条就 +2MB。service 文件没设 `MemoryMax`，所以内核 KILL → Restart=always → 死循环，counter 一路飙到 38。

### 2.4 BUY/SELL 过滤的现状

`trade_backfill.py:404-413` 已经在源头做过闸门：

```python
log_text = "\n".join(raw_logs)
is_sell = "Instruction: Sell" in log_text
is_buy = "Instruction: Buy" in log_text
if not (is_buy or is_sell):
    self._log_dirty_sample(sig, ...)
    continue
```

`trade_stream.py:167-178` 也有同样的闸门。所以"只保留 BUY/SELL"已经在做，过滤逻辑无需再加一层。**但 _log_dirty_sample 会保留 main/inner 非 dict 元素并打日志**，这部分未来可以视情况精简。

## 三、修复内容

### 3.1 service 加 OOM 防护

文件：`/etc/systemd/system/fastapiGmgn.service`

新增：
```ini
# === 2026-07-09 OOM 防护 ===
MemoryHigh=1G
MemoryMax=1200M
MemoryAccounting=true
Nice=5
```

- `MemoryHigh=1G` — 触发内核 reclaim，给别的进程让路
- `MemoryMax=1.2G` — systemd 硬上限，超了主动停（不会触发内核 SIGKILL）
- `Nice=5` — backfill CPU 抢占优先级降低一档

### 3.2 trade_backfill.py — 不再写 raw_data 进 Redis

文件：`/home/ubuntu/app/fastapiGmgn/app/services/trade_backfill.py:994`

```diff
-                "raw_data": str(tx)[:20000],
                 "source": "rpc_fill",
```

注释：完整 tx 已被 `_extract_trade_info` 消费，后续没人读 `raw_data` 字段。关闭后每条 detail 从 ~20KB → ~1KB，Redis 占用 -95%。

### 3.3 trade_stream.py — 不再写 raw_data 进 Redis

文件：`/home/ubuntu/app/fastapiGmgn/app/services/trade_stream.py:895`
