## 三、根本原因（**100% 锁定**）

### 卡顿来源

| 层级 | 耗时 | 结论 |
|------|------|------|
| `await _get_redis()` | 0ms | 正常 |
| `get_trader_state_with_sig` | 0ms | 正常 |
| `save_trader_state` | 1ms | 正常 |
| `zcard` + `hget` | 0ms | 正常 |
| **`ws.send_text` (内部)** | **1747-2551ms** | **❌ 慢在这里** |
| `json.dumps(_serialize)` | 0ms | 正常 |

**100% 锁定为 `app/websocket/manager.py` 的 `broadcast()` 函数**：

```python
async def broadcast(self, mint: str, message: dict):
    for ws in self.active_connections[mint]:
        try:
            await ws.send_text(json.dumps(_serialize(message)))  # ← 阻塞 1.7-2.5s
        except Exception as e:
            ...
```

### 为什么 `send_text` 慢？

`websockets` 库的 `send_text` 内部实现：

```python
async def send_text(self, data: str):
    await self.send(_encode_data(data))
```

`send` 内部：

1. 把数据写入 send buffer（极快）
2. **`await drain()` —— 等待 OS socket buffer 有空闲**（= 等客户端 ACK / 处理）

**当客户端（浏览器）处理速度跟不上时，OS buffer 写满，send 进入等 ACK 状态**。

### 为什么前端处理慢？

**前端 `trade_live.html` 的 `addTradeRow` 函数**：

- 每收到一条 trade 消息就 `tr.innerHTML = '...'` 拼一段 HTML
- `tbody.appendChild(tr)` 插入 DOM
- 5000+ 行 DOM 后，浏览器 O(N) 重排 + 重绘
- 浏览器在大量 DOM 操作时**接收 WebSocket 数据变慢**（JS 主线程被 DOM 占用）
- TCP backpressure 反馈到后端 → `send_text` 阻塞

**数据吻合**：每隔 10-20 笔出现 1 笔卡顿 = 前端 DOM 累积到 100-200 行时开始卡。
