# 全量计算"开始快，过了会慢" 问题诊断与修复报告

**测试 mint**: `HpZfpQEMwSuuN9zUJrMMr7QfuZ9tEjQGM6hBdNKqpump`
**总交易数**: 6477 (rpc_fill: 6311 + ws: 166)
**测试时间**: 2026-07-02
**日志文件**: `/tmp/server_final.log`

---

## 一、问题现象

启动服务后立刻触发"开始监听"，处理 5000+ 笔历史交易时：

- **前 30-50 笔**：每笔 3-10ms，流畅
- **之后**：每处理 10-20 笔就出现 1 笔 **1.5-2.8 秒** 卡顿
- **极端情况**：max 间隔 **4.5 秒**

---

## 二、诊断过程

### 2.1 第一次猜测：cluster 检测

**假设**：`_calculate_index` 内的 C006 cluster 检测慢。

**验证**：在 `cluster/detector.py` 加 `[C006-PERF]` 耗时打点。

**结果**：
- C006-PERF 4 条：**1.8-2.3s/次**
- 但日志中 >2s 间隔出现很多次，**远超 4 次** → 慢源不止 C006

### 2.2 第二次猜测：c008 dealer 检测

**假设**：C008 dealer 检测（5000+ 用户 HGETALL）慢。

**验证**：用户关闭 C008 后**仍然慢** → 排除。

### 2.3 第三次：扩大打点到主流程

**在 `_calculate_index` 加 5 段打点**：
- redis 取交易
- state 加载
- save 状态
- metrics 更新
- ws_manager.broadcast

**关键发现**：
```
[PF-SLOW] sig=4yhmF5Bm...
  redis_get=0ms  state=0ms  save=0ms  metrics=0ms  total=1751ms
[WS-BROADCAST] sig=4yhmF5Bm...  send=1747ms
```

**业务 5 段加起来 < 5ms**，但 total = 1751ms。
剩余 1745ms **完全在 `ws_manager.broadcast` 内部**。

### 2.4 第四次：定位到 ws.send_text

**`send_text = 1747ms`（与 PF-SLOW 误差 < 3ms）**。

`send_text` 内部 = `await ws.send_text(...)` 等同于 `await ws.send(...)`，
**WebSocket 协议层**的 `send` 在底层是同步等待 TCP ACK。

`send_text` 慢 = **客户端（前端浏览器）处理慢** = **TCP backpressure**。

### 2.5 第五次：前端验证

**问题链条**：
```
5000+ 笔 backfill 历史交易
  ↓ 每笔 ws.send_text(message) 给前端
每条消息 ~ 5-10KB（未精简）
  ↓
前端 onmessage 收到后 → 立刻 DOM 操作（insertBefore）
  ↓
DOM 节点数增加 → reflow/repaint 开销上升
  ↓
浏览器主线程被 DOM 操作占满
  ↓
WebSocket 帧处理排队 → TCP send buffer 满
  ↓
后端 ws.send_text 阻塞等待客户端 ACK
  ↓
后端 event loop 全部 await 都被卡住
  ↓
1.5-2.5s 业务"卡顿"
```

**最关键的 1 笔 4.5s 卡顿**（用户日志）：
```
PRE  00:23:55.198  [更新]: total_bet
POST 00:23:59.730  [cluster:redis:sync] 保存簇组
```
中间**完全没有日志**——业务代码在等 `ws.send_text` 返回。

---

## 三、根因总结

| 位置 | 表现 | 真因 |
|------|------|------|
| `app/websocket/manager.py` `broadcast()` | `send_text` 阻塞 1.5-2.5s | **前端 DOM 堆积 → 浏览器慢 → TCP backpressure** |
| `app/services/trade_processor.py` 主循环 | 业务卡顿 1.5-2.5s | 是上一行的**结果**，不是原因 |
| `app/services/cluster/detector.py` | 1.8-2.3s | 同样在等 `ws.send_text`，不是真因 |

**根因**：**后端 backfill 期间连续 5000+ 次高频推送 → 前端 DOM 累积 → 浏览器处理跟不上 → TCP backpressure → 后端 send_text 阻塞**。

---

## 四、修复方案

### 4.1 修复点 1 — 后端：backfill 期间不广播

**文件**: `app/services/trade_processor.py`

**思路**:
- 用全局 `_backfilling_mints: set` 标记 backfill 中的 mint
- 入口添加，finally 释放
- 3 个 `ws_manager.broadcast` 处加判断

**关键代码**:
```python
# 33 行：全局
_backfilling_mints: set = set()

# 847 行：run_full_calculation 入口
_backfilling_mints.add(mint)
try:
    ...
finally:
    _backfilling_mints.discard(mint)

# 660 行附近：_calculate_index 内的 broadcast 加判断
if mint not in _backfilling_mints:
    await ws_manager.broadcast(mint, trade_msg)
    if cluster_info:
        await ws_manager.broadcast(mint, cluster_matched_msg)
    if new_cluster_broadcast:
        await ws_manager.broadcast(mint, new_cluster_msg)
    await ws_manager.broadcast(mint, user_status_msg)
```

**为什么 `_calculate_index` 仍要加判断？** 实时交易也走 `_calculate_index`，backfill 期间实时新交易会**通过**判定发广播；旧交易虽 is_backfill=True 但加双保险。

### 4.2 修复点 2 — 前端：批量合并 + 限行

**文件**: `app/templates/trade_live.html`

**思路**:
- `addTradeRow` 拆出 `_buildTradeRow`（纯 DOM 创建）
- 加 `_pendingTrades` 数组缓冲
- 50ms 定时器统一 flush 一次
- 限行 500 笔

**关键代码**:
```javascript
let _pendingTrades = [];
let _flushTimer = null;
const MAX_ROWS = 500;

function _flushTrades() {
  const batch = _pendingTrades;
  _pendingTrades = [];
  _flushTimer = null;
  if (!batch.length) return;
  const frag = document.createDocumentFragment();
  batch.forEach(d => frag.appendChild(_buildTradeRow(d)));
  tradeTbody.insertBefore(frag, tradeTbody.firstChild);
  while (tradeTbody.children.length > MAX_ROWS) {
    tradeTbody.removeChild(tradeTbody.lastChild);
  }
  _updateTradeCount(batch.length);
}

ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === 'trade') {
    _pendingTrades.push(msg.data);
    if (!_flushTimer) _flushTimer = setTimeout(_flushTrades, 50);
  } else { _handleMessage(msg); }
};
```

**50ms 选择理由**: 人类视觉暂留 ~100ms，50ms = 3 帧，看起来"实时"，但避免每条都触发 reflow。

### 4.3 修复点 3 — 区分旧/新交易（防止漏发实时交易）

**文件**: `app/services/trade_processor.py`

**问题**: 仅按 `_backfilling_mints` 判断会漏发 backfill 期间的**实时**新交易。

**方案**: `_calculate_index` 加 `is_backfill` 参数，**只对 backfill 内的旧交易**不发广播。

```python
async def _calculate_index(tx_detail, mint, is_backfill=False):
    ...
    if not is_backfill and mint not in _backfilling_mints:
        # 旧交易 OR backfill 期间 → 不发
        # 实时交易（is_backfill=False, mint 不在 _backfilling_mints） → 发
        await ws_manager.broadcast(mint, trade_msg)
        ...

# backfill 主循环
await _calculate_index(tx_detail, mint, is_backfill=True)

# 实时链路
await _calculate_index(tx_detail, mint, is_backfill=False)
```

**修复点 1（_backfilling_mints）+ 修复点 3（is_backfill）= 双保险**：
- 即使 mint 已加 set，is_backfill=True 也不发（旧交易）
- 即使 is_backfill=False，mint 在 set 中也不发（极少见，防止 backfill 期间突发实时交易与 set 同步问题）

### 4.5 修复点 5 — 字段精简（白名单）

**问题**: backfill 期间 / backfill_done 推送的 trade 数据 5-10KB，100 笔约 1-2MB，超 WS 单帧 1MB 限制。

**方案**: 白名单制，只传前端 `_buildTradeRow` 实际用到的字段。

```python
# 932 行
_KEEP_FIELDS = {
    "sig", "from_address", "to_address", "amount", "token_symbol",
    "transaction_type", "sol_spent", "risk_score", "risk_indicators",
    "cu_consumed", "cu_limit", "collected_at", "wallet_tag",
    "block_time", "fee", "jito_tip", "priority_fee",
}
for s in recent_sigs:
    tx_full = txs_map.get(s)
    if not tx_full:
        continue
    tx = {k: tx_full.get(k) for k in _KEEP_FIELDS if k in tx_full}
    ri = tx.get("risk_indicators")
    if isinstance(ri, list) and len(ri) > 3:
        tx["risk_indicators"] = ri[:3]
    elif isinstance(ri, str) and len(ri) > 200:
        tx["risk_indicators"] = ri[:200] + "...]"
    recent_trades.append(tx)
```

**效果**: 100 笔 → 17 字段 → ~150KB（远低于 1MB WS 限制）。

### 4.6 修复点 6 — 顺序保证

**讨论**:
- 用户要求：展示顺序 = 旧的在下面，新的在上面
- 不能用"按 collected_at 排序"——同一秒的并发交易多
- 用户说"现在的顺序是 1. backfill 填充 获得的顺序 + ws 获得 的顺序"

**方案**: 用 `_processed_sigs` 记录 backfill 主循环**实际处理的 sig 顺序**——这就是指数计算的顺序。

```python
# 874, 886 行
_processed_sigs: list = []
for idx, sig in enumerate(all_sigs, start=1):
    await _calculate_index(tx_detail, mint, is_backfill=True)
    _processed_sigs.append(sig)  # 记录处理顺序

# 924 行
recent_sigs = _processed_sigs[-100:]  # 取最后 100 笔
```

**前端**: 倒序遍历 → 最新在表格顶部
```javascript
for (let i = rt.length - 1; i >= 0; i--) {
  tradeTbody.insertBefore(_buildTradeRow(rt[i]), tradeTbody.firstChild);
}
```

**为什么这样正确**:
- `all_sigs = rpc_sigs + ws_sigs`（主循环）
- `rpc_sigs` 是按 zset score 倒序（最新在 [0]）→ 主循环里**最旧先处理**（reversed 后从最旧到最新）
- **backfill 主循环顺序 = 从最旧到最新**（指数计算正确顺序）
- `_processed_sigs[-100:]` = **最新 100 笔**
- 前端倒序遍历 → 表格顶部是最新
